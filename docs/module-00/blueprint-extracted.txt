2. Product definition and value architecture
iSchoolie is education networking first, with courses, structured classes, official academic operations and professional
services integrated under one user identity. Familiar products such as LinkedIn, Udemy and Google Classroom serve as
feature-quality reference points, not as interface templates.
Primary personal learning loop. Institutional operations connect to this loop through authorized relationships only.

2.1 Goals and non-goals
Goals: one multi-role identity; safe discovery of educators; repeat learning; credible educator presence; operational
integrity for institutions; authorized guardian participation; enterprise-grade auditability and support.
Non-goals for automatic inclusion: full statutory payroll computation, unrestricted minor messaging, mandatory real-
time student transport tracking, custom national education board certifications, automatic AI final grading, and external
enterprise integrations not explicitly contracted.
Differentiation hypothesis: verified education identity connecting a learner/educator network to actual learning
outcomes and institution participation without making official records public.
Business validation: founding educator engagement, learner return frequency, institution workflow time saved, support
burden, trust incidents and paid conversion must be measured in private testing before mass launch.

3.1 Change and sign-off protocol
Each requirement receives a stable ID, version, source owner, priority, affected screens, permission policy, API/data
linkage, tests, and approval status.
Changes affecting minors, grades, access controls, finance or institution data require a product, domain-owner, security
and privacy impact review.
A change request records old behavior, new behavior, migration, compatibility, dependencies, tests, approver and
effective release.
Engineering may develop internal milestones, staging builds and invited pilots while public launch remains gated by
complete approved scope.
No requirement status is inferred as approved merely because this document contains an engineering recommendation.

4.1 Core role categories
Global categories: guest, learner, educator, guardian, tutor/mentor, moderator, safeguarding officer, support agent, platform
finance operator, platform administrator, security operator. Institution categories: account owner, principal, academic
director, department head, registrar, admissions officer, class/subject teacher, examination officer, attendance/timetable
coordinator, finance officer, accounts clerk, librarian, transport coordinator, hostel administrator, student welfare officer and
support staff. Detailed permissions are composed from assigned scopes, not hard-coded role name alone.
4.2 Authorization decision formula
ALLOW = active account AND authenticated session AND explicit resource entitlement AND permitted
tenant / relationship AND age / consent policy AND absence of block / suspension AND required action-
specific grant. 
Every list, detail, create, edit, delete, search, export, file, push, WebSocket, job, report and AI retrieval path must use the same
policy service or tested equivalent checks. Deny by default; return only the minimum permitted fields.

PART II / FUNCTIONAL REQUIREMENTS 
6. Complete 30-domain functional requirements
Coverage rule: the 30 domains below are the source-defined intended full-product areas. The five numbered FR statements
in each domain are proposed precise acceptance-oriented expansions, not an automatically approved replacement for the
original master. The source master remains preserved as the supporting record in the annex. Every domain must be
represented in scope tracking, architecture, UI, security and QA.
6.01 Public website [PUB]
Actors: Guest, candidate learner, educator, institution. Primary path: Home / discover / compare / register / support.
PUB-FR-01: Expose value propositions for learners, educators and institutions with accessible paths to login and
registration.
PUB-FR-02: Publish SEO-eligible public profiles, course detail pages, institution pages, communities, events and
opportunities only when the content is explicitly public.
PUB-FR-03: Support search facets and stable deep links without revealing private identities or institution records.
PUB-FR-04: Provide trust, safety, legal, pricing and support content with owned review/version dates.
PUB-FR-05: Offer institution registration and educator onboarding entry points and track consent-aware acquisition
attribution.
Security / data invariant: Any public response, CDN cache, sitemap or snippet must be derived exclusively from visibility-
approved data.
Failure and edge scenarios: Private profile removed from discovery; search engine cache; unpublished course; invalid locale;
guest tries protected link.
Acceptance gate: An anonymous request cannot retrieve an institution-private post, learner record, protected course lesson
or media object.
Web + mobile coverage: Web full; mobile via eligible in-app discovery and universal links.
6.02 Identity and authentication [AUTH]
Actors: Guest, registered user, account owner, security operator. Primary path: Register / verify / sign in / recover / switch
context.
AUTH-FR-01: Offer approved login methods, expiring verification challenges and safe recovery with anti-enumeration
responses.
AUTH-FR-02: Maintain secure sessions and device revocation; enforce suspension, deletion and account restrictions at
every access.
AUTH-FR-03: Support multiple eligible roles and institution memberships without user duplication or privilege self-
assignment.
AUTH-FR-04: Collect minimum onboarding data and apply approved age, consent and guardian authorization gates.
AUTH-FR-05: Require additional authenticated control for privileged actions, and audit session and role changes.
Security / data invariant: Role selection is not a grant; session claims cannot replace current authorization and relationship
checks.
Failure and edge scenarios: Expired token; duplicate contact; lost device; suspended user with cached mobile session;
attempted admin self-grant.
Acceptance gate: An altered registration body cannot create an institution administrator or platform operator account.
Web + mobile coverage: Web and mobile full; mobile secure storage and platform-appropriate sign-in.

6.03 User profiles [PROFILE]
Actors: Student, educator, tutor, guardian, public visitor. Primary path: Complete identity / edit / verify / preview / manage
visibility.
PROFILE-FR-01: Offer role-specific but unified profiles: education history, subjects, skills, work samples and
achievements.
PROFILE-FR-02: Separate public self-reported information from institution-controlled official student/staff records.
PROFILE-FR-03: Provide granular audience and search-index eligibility controls with a safe preview.
PROFILE-FR-04: Represent verification precisely by type, scope, evidence date and expiry where relevant.
PROFILE-FR-05: Retain historical affiliation changes without automatically disclosing confidential school data.
Security / data invariant: A public identity never serves as the authoritative source for official attendance, exam scores or
confidential welfare data.
Failure and edge scenarios: False affiliation; revoked verification; student becomes adult; blocked viewer; profile de-indexing
lag.
Acceptance gate: Profile preview and public API agree on visibility after relationship or privacy updates.
Web + mobile coverage: Web and mobile full; complex verification review web-first.
6.04 Education networking [NETWORK]
Actors: Eligible learner, educator, professional, institution. Primary path: Discover / follow / connect / block / remove.
NETWORK-FR-01: Allow follows and bilateral connection requests according to eligibility and age rules.
NETWORK-FR-02: Validate relationship and block status before creating suggestions or delivering invitations.
NETWORK-FR-03: Support withdraw, ignore, accept, remove, mute and restrict actions with idempotent transitions.
NETWORK-FR-04: Offer topic, role, language, institution and location filters only where privacy permits.
NETWORK-FR-05: Protect followers lists and recommendations from minor discovery or identity inference.
Security / data invariant: Connection or following is never sufficient to view a private institution record or a protected child
profile.
Failure and edge scenarios: Mutual requests; duplicated requests; blocked users; removed institution membership; high-
volume automated outreach.
Acceptance gate: Blocked or restricted accounts cannot contact one another via network APIs or discovery results.
Web + mobile coverage: Web and mobile full.
6.05 Educational feed [FEED]
Actors: Eligible author, reader, community moderator. Primary path: Compose / publish / consume / interact / report.
FEED-FR-01: Support audience-scoped text, image, document and permitted video posts with safe preview and
validation.
FEED-FR-02: Implement reactions, threaded replies, saved items, authorized resharing and author edits/deletes.
FEED-FR-03: Enforce audience selection across feed queries, notifications, search, CDN and attachments.
FEED-FR-04: Provide a simple relevant feed first: recency, relationships, interests, quality and safety signals.
FEED-FR-05: Support explainable mute, report, block, hide and preference mechanisms and moderation removal.
Security / data invariant: Every feed read rechecks post visibility, tenant audience, block, age and content status.
Failure and edge scenarios: Deleted post in cached feed; private post reshared; attachment link copied; offline duplicate
reaction.
Acceptance gate: A school-only post is absent from public timeline, public search and unauthorized file URLs.
Web + mobile coverage: Web and mobile full; mobile cursor pagination and virtualization.

6.06 Communities [COM]
Actors: Member, applicant, founder, moderator. Primary path: Create / request join / approve / publish / moderate / leave.
COM-FR-01: Support public, private and institution-restricted communities with distinct eligibility rules.
COM-FR-02: Configure ownership, topic, description, rules, moderators, join applications and membership bans.
COM-FR-03: Offer community posts, discussions, resources, announcements and eligible event linkage.
COM-FR-04: Audit administrative changes and moderation actions while permitting appeals where applicable.
COM-FR-05: Re-evaluate eligibility when a user loses membership in the owning institution.
Security / data invariant: Private content requires active authorized membership, not knowledge of a group ID.
Failure and edge scenarios: Founding owner leaves; member suspended; institution terminates access; replayed approval
invitation.
Acceptance gate: An unapproved applicant cannot read private posts or obtain their attachments.
Web + mobile coverage: Web and mobile full; advanced management web-first.
6.07 Learning Management System LMS
Actors: Educator, course owner, student, institution. Primary path: Draft / validate / publish / enroll / learn / complete.
LMS-FR-01: Create courses with outcomes, prerequisites, instructor, subject, levels, language and entitlement rules.
LMS-FR-02: Maintain ordered modules, lessons, resources, curriculum versions and explicit publication workflows.
LMS-FR-03: Support free and entitled paid enrollment, cross-device progress and downloadable resources only when
authorized.
LMS-FR-04: Separate independent marketplace courses from institution-owned classroom offerings and rosters.
LMS-FR-05: Issue completion records and eligible certificates only after confirmed course rules are met.
Security / data invariant: Enrollment and paid entitlement are backend authoritative; lessons remain protected even through
copied URLs.
Failure and edge scenarios: Course republished while enrolled; version migration; stale offline progress; instructor removed;
payment reversal.
Acceptance gate: Duplicate enrollment requests result in one valid entitlement and consistent learner progress.
Web + mobile coverage: Web and mobile learning full; advanced authoring web-first with supported mobile edits.
6.08 Assignments and assessments [ASMT]
Actors: Teacher, learner, grader, examination officer. Primary path: Assign / submit / grade / review / release.
ASMT-FR-01: Create assignments with eligibility, deadlines, attempts, submission types and optional rubrics.
ASMT-FR-02: Offer draft, publish, submit, resubmit where allowed, late-policy evaluation and feedback delivery.
ASMT-FR-03: Support configured question types, answer persistence, time limits and appropriate auto-scoring.
ASMT-FR-04: Enforce grading rights, version history, publication timing, appeal and correction workflows.
ASMT-FR-05: Protect learner submissions, scores and unpublished results from peers and unauthorized guardians.
Security / data invariant: The authoritative grade is never derived solely from client input; publication is an explicit authorized
transition.
Failure and edge scenarios: Network failure at deadline; interrupted assessment; simultaneous attempts; rubric change after
submission.
Acceptance gate: One student cannot view another student submission or change a published grade.
Web + mobile coverage: Web full; mobile learner flows and teacher quick actions, complex question authoring web-first.

6.09 Live learning [LIVE]
Actors: Teacher, student, authorized guardian and institution. Primary path: Schedule / authorize / join / host / record /
finish.
LIVE-FR-01: Schedule classroom sessions with roster, start/end time, timezone and attendance policy.
LIVE-FR-02: Generate short-lived participant/host credentials after current authorization checks.
LIVE-FR-03: Provide host moderation controls, approved chat and participation safeguards for minors.
LIVE-FR-04: Record participation and integrate with academic attendance only by approved business rules.
LIVE-FR-05: Control recordings, consent, retention, playback rights and third-party provider failure states.
Security / data invariant: A copied room link or expired membership cannot grant access to an institution-private class.
Failure and edge scenarios: Provider outage; participant rejoins; token reuse; late attendance; revoked educator host rights.
Acceptance gate: Revocation blocks new joins and protected recordings; classroom attendance is not duplicated on
reconnect.
Web + mobile coverage: Web, Android and iOS participant/host essentials.
6.10 Institution management [INST]
Actors: Institution owner, principal, delegated administrator. Primary path: Apply / verify / configure / invite / operate /
suspend.
INST-FR-01: Create verified institution workspace with separate public identity and private tenant settings.
INST-FR-02: Support scoped staff, learner, guardian and vendor memberships, roles, delegated grants and audit.
INST-FR-03: Create institution academic structure, private announcements, member groups and programs.
INST-FR-04: Offer controlled activation, suspension, transfer of ownership, export and offboarding lifecycle.
INST-FR-05: Define optional SSO, roster import, external integrations and negotiated enterprise service commitments.
Security / data invariant: Institution A cannot list, access, export, query, cache or receive Institution B private resources.
Failure and edge scenarios: Admin removed mid-session; mistaken tenant slug; institution merger; transfer of ownership;
expired invitations.
Acceptance gate: Cross-tenant denial is verified across endpoints, exports, background jobs, search and object storage.
Web + mobile coverage: Full web administration; selected mobile institution operations, reporting and approvals.
6.11 Admissions [ADMS]
Actors: Applicant, guardian, registrar, reviewer. Primary path: Configure cycle / apply / review / offer / enroll.
ADMS-FR-01: Configure admission cycles, program eligibility, published forms, required evidence and application
deadlines.
ADMS-FR-02: Accept accessible saved drafts and protected uploads with review, correction request and decision
history.
ADMS-FR-03: Use offer, acceptance and expiration steps when configured by the institution.
ADMS-FR-04: Convert accepted applicants to student records using deduplicated transaction and student-number
policy.
ADMS-FR-05: Support withdrawals, rejection reason policy and privacy-aware applicant notification.
Security / data invariant: Only authorized admissions staff can make institutional decisions; a completed application never
self-enrolls.
Failure and edge scenarios: Applicant has existing student record; withdrawn offer; corrected document; concurrent
acceptance.
Acceptance gate: A replayed approved application does not create two active student records.
Web + mobile coverage: Web full; mobile application and applicant status; admissions back office web-first.

6.12 Student Information System [SIS]
Actors: Registrar, academic administrator, student, guardian. Primary path: Create official record / enroll / transfer /
graduate / withdraw.
SIS-FR-01: Maintain official student record, institution-scoped number, effective dates, status and linked account if
approved.
SIS-FR-02: Manage academic history, year/program/section assignment, transfer and graduation with traceable changes.
SIS-FR-03: Link one person to multiple institution records without copying confidential data across tenants.
SIS-FR-04: Authorize field-level views and exports for staff, students and guardians independently.
SIS-FR-05: Support import, duplicate detection, merge review, archival and retention policies.
Security / data invariant: Official student data has institution ownership and must not inherit public profile permissions.
Failure and edge scenarios: Name correction; student moves schools; duplicate imported student; shared guardian; alumni
access.
Acceptance gate: Institution record changes preserve history, authorship and effective dates; unauthorized records remain
invisible.
Web + mobile coverage: Web full back office; mobile self-service and authorized teacher/guardian views.
6.13 Academic structure [ACA]
Actors: Academic administrator, department head, teacher. Primary path: Configure academic years / terms / programs /

8.3 Responsive and cross-platform behavior
Shared: one account, synchronized server state, normalized IDs, consistent permissions, internationalizable strings,
discoverability policies, consistent accessibility meaning.
Web: accessible complex tables and filters, multi-column admin workflows, drag/drop where keyboard alternative exists,
full reporting and approved exports.
Android: native back navigation, secure storage, notification channels, media permissions, interrupted network recovery,
safe activity resume.
iOS: safe-area and native gestures, Apple push, dynamic text, permission prompts, background/resume handling and
platform-appropriate account settings.
Offline: permit explicitly approved cached reading and draft saves; never treat offline grades, fees, consent, entitlements
or role grants as authoritative. Submit through idempotent sync when online.
Deep links: every destination rechecks session, workspace, age and object permissions; external links never carry
reusable administrative or live-session tokens.
Multi-account/session: support sign-out, device revocation and controlled return to original account context without
residual tenant or child data.

11.15 Data domain ownership and boundaries
Only the institution context can authoritatively modify student_records, official attendance, official examination results
and fee ledger entries.
A public course enrollment never automatically imports a learner into a school or makes academic history public.
Guardian access points to the authoritative institution student record through a verified scoped relationship.
A global user may hold several institution memberships, but a private record remains associated with its original owning
institution.
Accounting entries, grade changes, security and safeguarding actions are append-only or otherwise auditable according
to approved rules.
Search, analytics, object storage and AI knowledge retrieval respect the same tenant and relationship policies as primary
APIs.
Deletion, retention and anonymization must follow approved object-specific rules and applicable legal exceptions; a
global account deletion does not arbitrarily delete statutory institution records.
11.16 Indexing, transaction and migration strategy
Prefer composite indexes for (institution_id, academic_year_id, class_section_id) and common learner-record
lookups; verify plans with production-like data.
Use cursor pagination for feed/messages and deterministic ordering with stable ID tie breakers.
Treat admission conversion, attendance finalize, grade publish, checkout entitlement and fee allocation as transactionally
protected workflows.
Require idempotency keys for financial and repeatable client mutations; preserve provider event IDs and reconciliation
evidence.
Use expand-and-contract migrations in rolling deployments; backfill, validate, switch reads, then remove old
representations after a retention period.
Define retention tables, backup restoration schedules, foreign key behavior and partitioning strategy based on observed
volume rather than guesses.

12.1 Required request/response contract fields
Every endpoint: HTTP method, path, purpose, authentication, actor scopes, tenant context, age/guardian requirements,
input schema, output schema, error codes, rate limits, idempotency, audit effect and test coverage.
Errors: consistent code, message safe for disclosure, correlation ID, remediation hint and field-level validation errors;
never expose DB internals or permission evaluation secrets.
Pagination: stable cursor and page limit, explicit sort, total count only if safe/performant; never return unbounded lists.
Write operations: optimistic revision/ETag where needed; conditional update and conflict code; business timestamp
comes from server.
Media: authorize upload intent, enforce size/type, quarantine/scan, transform and issue short-lived scoped access URL.

12.4 Real-time delivery contract
Socket channels are delivery paths, not sources of truth. Persist conversation, attendance, learning or booking changes before

conversation.read.updated, typing.started, typing.stopped, notification.created, booking.updated, live-
session.state-changed. Event payloads must be minimum sufficient, ordered or versioned as appropriate, and safe for
access revocation.

14.2 Mandatory threats and abuse cases
An unassigned educator tries editing a class attendance or grade using a guessed ID.
A guardian switches children and obtains stale cached or direct-linked data from another child.
A member of Tenant A alters path or body to access Tenant B student records, reports, media or backup.
A minor is recommended to or contacted by a prohibited adult through follows, DMs, groups or course invitations.
A suspended teacher attempts using a previous mobile token, signed URL or live-session link.
A forged webhook or repeated provider callback triggers duplicate entitlement, payout, fee allocation or refund.
A malicious student upload contains executable content, hidden script or unsafe media; scanning and sandbox policy
applies.
An AI request smuggles private school data or injects instructions in a retrieved document.
An operator attempts to browse student welfare records outside an assigned safety investigation.
An internal export/report aggregates very small cohorts or identifies protected children.
